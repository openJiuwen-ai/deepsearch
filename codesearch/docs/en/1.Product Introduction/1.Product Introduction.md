# Product Introduction

**openJiuwen-CodeSearch** is an agentic retrieval engine for code repositories.
Given a problem statement — a GitHub issue, a bug report, a feature request — it
returns the files and line ranges you need to look at. Built on openJiuwen
agent-core, a retrieval agent autonomously inspects the repository map, runs
multi-strategy searches, expands context, curates findings, and submits results.

## Use cases

- **Fault localization**: turn an issue into the exact functions and lines that
  need changing — the first stage of an issue-to-patch pipeline.
- **Context supply for code Q&A**: answer "where is this implemented?" or
  "where does this error come from?" with line-level evidence.
- **Large repository navigation**: trade a natural-language description for
  relevant code slices in an unfamiliar codebase.

## Core capabilities

### Agentic multi-turn retrieval

The agent has five tools: view the repository file map, search the codebase with
multiple strategies, expand a line range, drop false positives, and submit the
final answer. It decides its own next move across turns, accumulating relevant
snippets until confident enough to submit.

A two-model design keeps cost under control: a capable model drives search
decisions, while a lightweight model extracts the truly relevant lines from each
retrieved chunk — so the capable model only ever sees curated content.

### Code-aware hybrid indexing

- **Syntax-aware chunking** along function and class boundaries, so every chunk
  is a complete semantic unit. **Python (`.py`) only for now**; other languages
  need a custom `Chunker`.
- **Dual sparse retrieval**: token BM25 for semantic keywords, character trigram
  BM25 for exact substrings such as `data.sum()` or stack traces.
- **Incremental indexing**: content-hash deduplication lets multiple revisions
  share the index of unchanged files, making re-indexing nearly free.
- **Optional dense retrieval** fused with sparse results by weighted ranking.

### Two equivalent execution engines

The retrieval loop runs either as an openJiuwen workflow graph (default, with
node-level observability) or as a plain code loop (framework-free fallback).
Both share one implementation of the loop stages; tests lock their outputs to be
byte-identical.

### Service-ready engineering

Multiple delivery forms (source, Docker image, official wheels including
`openjiuwen-search-base`), per-request run isolation, multi-product coexistence
on a shared Milvus instance, timeouts, bounded concurrency, and token
accounting. The HTTP service has **no authentication**; indexing is gated by
the `CODESEARCH_INDEX_ROOTS` whitelist (refused when unset).

## Architecture

```
┌──────────── Indexing (offline) ─────────────┐
│ repository → syntax-aware chunking          │
│           → Milvus dual sparse indexes      │
│ incremental: content-hash dedup across revs │
└─────────────────────────────────────────────┘
┌──────────── Retrieval (online) ─────────────┐
│ problem statement → retrieval agent         │
│   (decision model · filter model · snippet  │
│    memory · five tools) → files + lines     │
└─────────────────────────────────────────────┘
```

Layers depend in one direction: `domain ← config ← algorithm ← framework ← api`.
Shared search capabilities live in the standalone `openjiuwen-search-base`
package. See the [Developer Guide](../4.Developer%20Guide/README.md).
